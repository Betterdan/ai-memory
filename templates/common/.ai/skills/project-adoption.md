# 已有项目接入

用于已有代码、规则或 Wiki 的项目首次接入。已初始化的项目先用 `ai-memory update --dry-run` 核对版本和所有权，按需要补充本协议中的产物。

## 建立框架

1. 清点项目根、Git 基线、现有工具入口和配置、团队规范、模块规则、个人偏好以及历史 Wiki。确认本次补档的代码提交、范围和负责人。仅有源码快照时记录快照来源和证据标识；实际分支及部署状态单独核实。
2. 在项目根执行 `ai-memory init --adopt --yes`，按需用 `--tools` 选择适配层。检查保留项和入口 diff。已有入口的 frontmatter 留在文件顶部，原正文先完整留在 user 区块，受管区块负责加载框架。已有 Claude 设置继续由项目管理；根据团队约定人工合入需要的 hook。

## 逐条归并规则

1. 将现有 `AGENTS.md`、`CLAUDE.md`、模块指令、团队规范和适用 Wiki 条款拆成可核对的规则。记录来源位置、适用路径或任务、触发条件、约束强度，并与 `.ai/` 中的框架、团队、项目公共、模块和个人各层已生效规则对照。
2. 等价时复用已有条款；覆盖部分相同时仅补实际参数、约束或明确例外；新增规则放进最窄适用层；强制规则冲突时记录双方、适用范围和待裁定事项。仅在条件、范围和强度一致时合并同义规则。按顺序加载规则时，个人偏好可细化允许调整的默认项，例外仍以规则所有者明确授权为依据。
3. 把共享规则正文和链接收敛到 `.ai/knowledge/conventions.md` 的规则索引及其指向的项目文档。已有规范已有可靠入口时沿用链接；前后端或其他模块按路径加载。两侧工具入口的 user 区块只保留必要导航和工具特有指令。对照归并记录核对每条规则的去处，再精简 user 区块中的重复正文。个人信息和私有路径留在合适的本地或用户记忆中。
4. 核对计划用作 worktree 基线的提交是否包含启用工具的根入口、`.ai/README.md`、`knowledge/conventions.md` 及其指向的共享规则。被 Git 忽略的入口或私有来源应在每个 worktree 单独配置。让 Agent 在项目根和独立 worktree 各跑一次只读加载，报告实际读取的入口、规则文件及一条代表性约束。用 `ai-memory update --dry-run` 复核框架仍可升级。

## 建立第一版知识基线

1. 全局清点范围内的代码模块、对外入口和历史 Wiki 导航，再选择关键入口和领域分批核对。保留原始 Wiki。已审阅材料可用作核验线索，历史、候选和需求资料要带上各自的时间与状态。
2. 按 `knowledge-structure.md` 的「历史功能首次补档」核对代码、测试、契约与可用配置。记录每条结论的证据位置和基线。实际运行或上线证据缺失时，精确记录静态结论与待验证范围。把尚未裁定的差异放进独立的补档记录，待确认后再并入正式页面。
3. 写入项目概览、必要的架构基线、入口与领域页。概览注明已覆盖、待确认和未覆盖的模块，并连接补档记录。执行 `ai-memory kb build`、`ai-memory kb check` 和 `ai-memory kb export`，检查导航和导出内容后提交负责人复核。
