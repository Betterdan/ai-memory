# 风险等级与退出条件

S/M/L 决定流程深度,不代表需求价值。拿不准时选高一级,并在实现交接中写明原因。
**本文件是各等级行为的单一事实源**;其他方法论文件只引用本文件,不重复定义等级行为。

## 判断

| 等级 | 判断 |
|---|---|
| S | 局部、可逆,不跨模块/数据/部署边界,验收标准明确 |
| M | 跨多个模块,或改变数据、公共接口、运行行为 |
| L | 改变系统边界、数据所有权、部署拓扑,或安全/迁移/可用性风险高 |

## 跨等级硬门槛

以下规则不因等级降低而豁免:

- **对外接口契约**:改变对外可观察接口时,必须先更新契约并由用户确认 diff,才能开始实现。判定边界与通过条件见 `.ai/skills/interface-contract.md`。

## S 级:轻量独立路径

S 级是独立路径,不是 M 级的简化版。

**执行**

1. 直接实现,遵循需求的外部行为契约。
2. 运行与本次改动相关的测试。
3. 测试失败时最多修复 2 次;第 3 次仍失败就停下,把失败输出和已尝试的修复交给用户,不继续猜测。

**退出条件**(同时满足即完成)

- 相关测试全部通过
- 改动未超出需求写明的范围
- 涉及对外接口变更时,契约已更新并经用户确认

**不做**

- 不做 critic 自检,也不启动独立 critic
- 不创建 handoff,即使 `model-routing.json` 的 profile 不是 `inherit`
- 不生成技术设计,不做方案比较和实施计划
- 不生成交付就绪报告
- 不启动完整 code review 流程;提交前仍逐条对照验收标准
- 只有项目状态真实变化时才更新知识;纯局部修复不写记忆

S 级不豁免上方的跨等级硬门槛:改动触及对外可观察接口时,同样先过契约门槛再实现。

## M 级:精简完整路径

**执行**

1. 按 `.ai/skills/feature-design.md` 生成聚焦实际变化的精简设计。
2. 按 `.ai/skills/critic.md` 做一次精简自检;工具支持独立上下文时优先使用独立 critic。
3. 实现并补齐覆盖验收标准的测试。
4. 按 `.ai/skills/delivery-readiness.md` 检查适用项。

**退出条件**(同时满足即完成)

- 验收标准逐条有测试或可复现的证据
- 技术接口契约与实现一致,错误路径有定义
- critic 质疑全部处理完毕:接受并修改,或给出理由反驳
- 交付就绪结论为 `ready` 或 `conditional`,且条件已写明
- 稳定决策与契约变化已写入知识

**不做**

- 不为未出现的变化场景预留抽象
- 设计已可实施时不做方案比较和实施计划

## L 级:完整路径

**执行**

1. 先更新 `docs/architecture/` 基线,再执行完整 `feature-design`。
2. 对未决的高影响选择做一次方案比较;需要分阶段落地时给出实施计划。
3. 按 `.ai/skills/critic.md` 做独立对抗性检查。
4. 按 `.ai/skills/delivery-readiness.md` 做完整检查。

**退出条件**(同时满足即完成)

- M 级的全部退出条件
- 项目基线已反映新的边界、数据所有权或部署拓扑
- 迁移与回滚路径已验证,不是只有方向
- 交付就绪结论为 `ready`,阻塞项清零
- 新决策与被推翻的旧决策都已记录

**不做**

- 不把基线更新推迟到实现之后
- 不用「未来可能扩展」代替具体的负载或变化场景

## 升级与降级

- 实现中发现改动跨出了原判断的边界,立即升级等级并补齐对应产物,不在低等级下继续。
- 不为省流程而降级;只有范围真实收窄时才降级,并由用户确认。
