# 代码审查(review)

输入:本次变更的 diff、对应 final 需求的外部行为契约与验收标准、适用的 `docs/design/` 技术接口契约和验证证据。输出:带证据的问题列表或明确通过。

## 触发时机

- 实现完成,准备提交或合并前。
- 已审出的问题修复完成后重新审查。
- 用户明确要求 review。

不为单个测试改动、格式化或纯文档变更启动完整审查。

## 流程

1. 先读契约再读代码:final 需求的外部行为契约与验收标准,以及适用设计的技术接口契约。
2. 把 diff 逐条对照验收标准,标记覆盖、部分覆盖或未覆盖。
3. 按下方检查项审查;不适用项写明原因,不静默跳过。
4. 按 `P0` 阻塞 / `P1` 应修 / `P2` 可选输出,每条给出位置、触发条件和证据。
5. 第一轮保持只读,不直接修复;修复由实现方完成后重新审查。

## 检查项

- **契约一致**:实现与 `final/*.md` 的外部行为契约、验收标准及适用的 `docs/design/` 技术接口逐条对照
- **契约门槛**:改动触及对外可观察接口时,契约文件已更新且 diff 已确认(见 `.ai/skills/interface-contract.md`)
- **错误路径**:失败表达与契约声明一致,没有吞掉错误
- **知识同步**:对外可观察行为变化已合并进 `.ai/knowledge/` 对应入口页或领域页
- **范围**:未引入需求「不做什么」里排除的内容
- **简洁**:没有单人项目不需要的抽象(YAGNI)

启用模型路由时,`final-review` 按 `.ai/skills/model-routing.md` 解析执行等级;只传 handoff、正式文档路径、diff 和验证证据,不传对话历史。
